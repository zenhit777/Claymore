Le test critique n° 10 a été exécuté dans les deux campagnes avec la sortie :

```text
M5-HW-POLL-01 retired=1; admission evicted completed victim without explicit wait
```

Il appelle `poll_completed_transfers` jusqu'à obtenir `retired=1`, puis effectue une admission (`allocate_device("replacement", ...)`) **sans** appel préalable à `wait_for_transfer` ni `wait_for_allocation`. Le manager retire donc l'event terminé par polling, lève les gardes de l'allocation victime, évince celle-ci et admet le remplacement. Le test vérifie ensuite que `usage_bytes(Vram)` vaut 512 KiB et que la victime n'est plus libérable (`UnknownAllocation`).

## 8. Anomalies, avertissements et limitations

### 8.1 Avertissements sans impact

- Cargo émet des avertissements de manifeste préexistants : champ `workspace.package.repository` inutilisé, dépendances `thiserror` et `claymore-core` déclarées mais inutilisées dans certains crates. Ces avertissements ne concernent pas les tests CUDA et n'ont produit aucune erreur.
- Le GPU était partagé avec le compositeur Windows/Xwayland (environ 1 395 MiB utilisés au début de la campagne). Les tests utilisent de petites allocations (jusqu'à 64 MiB dans `hw_c3_01`) et disposaient d'environ 30 GiB libres. Aucun échec d'allocation n'a été observé.

### 8.2 Variabilité observée

Les assertions des tests sont sémantiques, pas des seuils de performance. Les valeurs suivantes varient entre les deux campagnes sans changer le résultat :

| Mesure | Campagne 1 | Campagne 2 |
|---|---:|---:|
| `hw_c6_01` — requêtes de polling avant éviction | 489 | 114 |
| `hw_c7_01` — 128 cycles H2D/D2H | 105,93 ms | 100,18 ms |
| `hw_m7_...executor` — H2D 1 MiB | 128 862 ns | 114 862 ns |
| `hw_m7_...executor` — D2H 1 MiB | 74 981 ns | 86 121 ns |
| `hw_m7_...executor` — attente event | 133 832 ns | 149 212 ns |

Cette variabilité est attendue sur un GPU partagé avec l'affichage et sous WSL2. Elle n'indique ni régression ni instabilité : les deux campagnes sont intégralement vertes.

### 8.3 Limitations de périmètre

- La campagne ne valide **aucun kernel tensoriel**, aucun calcul matriciel, aucune inférence et aucune génération de modèle.
- Elle ne valide pas les performances M8, les charges soutenues du cache d'experts, ni les scénarios de contention multi-utilisateur.
- Elle n'inclut ni Compute Sanitizer, ni injection de fautes CUDA, ni test de récupération après erreur matérielle.
- Elle est limitée à un seul GPU RTX 5090 et à WSL2 ; elle ne constitue pas une validation Windows-native ou multi-GPU.
- `--test-threads=1` sérialise volontairement les tests matériels ; aucun stress de concurrence multi-thread sur le manager n'est revendiqué.
- La commande workspace exécute 27 tests matériels, dont les 17 requis. Le résultat 27/27 ne doit pas être présenté comme « 17 tests » : le résultat requis est bien 17/17, et le total observé est 27/27.

### 8.4 Corrections de code

Aucune correction de code n'a été nécessaire. Aucun fichier Rust, aucune API, aucune configuration Cargo et aucun marqueur de test n'ont été modifiés pendant la campagne. Le commit documentaire ne contient que le présent rapport et les logs bruts.

Cette validation couvre uniquement le périmètre CUDA mémoire et transferts décrit ci-dessus. Elle ne revendique ni kernels tensoriels, ni génération de modèle, ni performances M8. La PR #22 n'a pas été fusionnée.
