# M11.1 — Addendum d'audit et corrections factuelles (2026-11-26)

Ce document complète le rapport `m11.1-clover-checkpoint-audit-2026-11-26.md`. En cas de divergence, le présent addendum prévaut pour les points explicitement corrigés ci-dessous. Il ne modifie ni les révisions upstream, ni les empreintes épinglées, ni le schéma des tenseurs.

## 1. Correction sur la taille des blocs SHA-256

Le rapport initial (§ 11, observation L2) indique que `sha256_file` traite les fichiers par blocs de 8 MiB via `MAX_CHUNK_BYTES`. Cette formulation est inexacte pour l'implémentation effectivement appelée par `CloverCheckpointInventory::verify_pinned_asset_hashes` :

- `verify_pinned_asset_hashes` appelle `sha256_file`.
- `sha256_file` appelle `sha256_reader`.
- `sha256_reader` utilise un tampon de lecture de **1 MiB** (`1024 * 1024` octets).
- `Sha256Stream::update` traite les octets reçus sans allocation proportionnelle à la taille totale du fichier.

Le constat de débit (environ 21 MB/s dans l'environnement décrit au rapport) reste une mesure observée, mais l'attribution à des blocs de 8 MiB est retirée. Aucune conclusion de sécurité ou de performance ne doit être tirée de cette taille erronée.

## 2. Défaut découvert et corrigé dans Sha256Stream

La revue du code a révélé un défaut dans `Sha256Stream::update` : lorsqu'un appel précédent laissait un bloc partiel en mémoire et que l'appel suivant apportait trop peu d'octets pour compléter les 64 octets, le chemin de traitement réinitialisait à tort le compteur de données tamponnées. Un lecteur conforme au trait Rust `Read` peut légalement renvoyer des lectures courtes ; l'implémentation devait donc préserver les fragments incomplets entre appels.

Correction appliquée sur `feat/m11-clover-foundation` :

- Commit : `7ee60fff9962c9b8cc05831eb854471deba05931`.
- Le bloc partiel est maintenant conservé si l'entrée suivante ne complète pas le bloc SHA-256.
- Le test de non-régression couvre plusieurs tailles de fragments (dont 1, 2, 7, 13, 31, 63 et 65 octets), des frontières de padding, ainsi qu'un lecteur qui renvoie volontairement des lectures courtes de 13 octets.
- CI Rust stable et Rust 1.86 : succès, run [45857457002](https://github.com/zenhit777/Claymore/actions/runs/45857457002), 2/2 jobs réussis.

**Limite de preuve à conserver :** la campagne de hachage complète de 69,3 GB consignée dans le rapport a été exécutée avant ce correctif. Les 28 empreintes ont également été calculées avec `sha256sum` et comparées à la table épinglée (28/28). Le nouveau test démontre le comportement corrigé sur les fragments courts ; le hachage intégral de 69,3 GB n'a pas été rejoué après le commit `7ee60fff`. Ne pas présenter le journal historique comme une exécution de ce nouveau SHA.

## 6. Plan de chargement metadata-only ajouté après l'audit initial

Le critère M11.1 de plan shard/tensor/chunk, initialement non couvert par les journaux historiques, est maintenant implémenté dans le code :

- `CloverCheckpointInventory::load_plan()` dérive un plan déterministe à partir des offsets validés des headers Safetensors.
- Le plan expose les shards, les tenseurs ordonnés par offset physique, les offsets relatifs au tenseur et au payload du shard, ainsi que les longueurs de chunks.
- Chaque chunk est borné par `claymore_checkpoint::safetensors::MAX_CHUNK_BYTES` (8 MiB).
- `inspect_checkpoint` affiche le nombre de shards, tenseurs et chunks prévus, ainsi que la taille maximale des chunks.
- Les tests couvrent les frontières 8 MiB, les offsets et l'assemblage du plan sur un checkpoint synthétique.

Cette planification ne lit pas les payloads, n'alloue aucun tenseur et ne réserve aucune VRAM. Elle constitue un contrat de planification, pas encore un ordonnanceur de lecture ni une intégration au MemoryOrchestrator ; ces comportements relèvent des phases suivantes.

## 7. Contrôle du dtype des sidecars GDN

La revue du chemin de validation a aussi identifié que `inspect` imposait BF16 aux 26 shards de modèle, mais exemptait les deux sidecars GDN de cette contrainte. Or l'audit du checkpoint épinglé constate que les 120 tenseurs sidecar sont eux aussi stockés en BF16. L'exemption aurait donc laissé passer un checkpoint altéré avec un sidecar F32.

Correction appliquée :

- Tous les tenseurs des 28 artefacts épinglés, sidecars compris, doivent maintenant être BF16 à l'inspection.
- Un test négatif construit un sidecar GDN F32 et vérifie son rejet par `CloverCheckpointInventory::inspect`.
- Commit : `f23fc1b55592b8e7a44a4c021c5f6495befc6506`.
- La CI de ce commit est en cours au moment de la rédaction ; ne pas déclarer ce correctif validé avant son succès complet.

## 8. Parité de tokenisation du chat template : preuve antérieure insuffisante

La revue du script `m11.1-chat-template-audit.py` a révélé que le champ historique `roundtrip_ids_stable` comparait deux fois le même appel de tokenisation du texte rendu. Cette assertion était tautologique et ne prouvait pas l'équivalence entre les deux chemins de l'API Transformers.

Correction du script :

- Le chemin direct utilise maintenant `tokenizer.apply_chat_template(messages, tokenize=True)`.
- Le chemin rendu utilise `tokenizer.apply_chat_template(messages, tokenize=False)`, puis retokenise le texte avec `add_special_tokens=False`.
- Les deux listes d'identifiants sont enregistrées séparément et comparées réellement.
- Commit du script : `19162398d2fadb48cd9a72dac0f0801e1d38f50f`.

Les 12 rendus publiés et les trois rejets négatifs attendus restent des observations utiles. En revanche, les champs historiques `roundtrip_ids_stable=true` ne sont pas une preuve de parité. Le JSON de fixtures doit être régénéré sur le checkpoint local avec le script corrigé avant d'affirmer cette parité. Cette tâche est CPU-only ; le mandat reproductible est fourni dans `docs/audits/prompts/m11.1-cpu-evidence-refresh-agent.md`.

Le script corrigé refuse maintenant aussi les rejets inattendus : F10, F11 et F12 ne sont considérés comme attendus que si le type d'exception et le motif correspondent aux erreurs prévues ; toute divergence de token IDs ou toute erreur inattendue fait sortir le script avec un code non nul. Correctifs complémentaires : `7d0b3271c7a6a2bf23ba3334f58bea2ea721d45f` et `7d5685a9e04491352c3c3d940acb20511978d184`.

### 10.1 Nouveau défaut d'outillage, trouvé par ce rafraîchissement

La version du script de parité produite par `1916239` / `7d0b327` / `7d5685a` comparait
`list(apply_chat_template(..., tokenize=True))` aux identifiants du rendu. `apply_chat_template`
renvoie un **`BatchEncoding`** (dérivé de `UserDict`, donc **non** `dict`) : `list(...)` y itère sur
les **clés**. La liste comparée valait `["input_ids", "attention_mask"]`, et les **9 cas positifs
échouaient** avec `ECHEC_INATTENDU` (sortie 1) — la porte était fail-closed, mais fausse.

Correctif appliqué (extraction de `input_ids`, dé-batching le cas échéant), puis régénération des
deux sorties brutes et du fichier de fixtures. Les chaînes rendues, les `token_ids`, les compteurs,
les statuts et les messages d'erreur restent **inchangés** par rapport à la preuve publiée : seule
la preuve de parité change de nature. Empreintes de la chaîne de versions du script :
`m11.1-postfix-2026-11-26-script-digests.txt`.
