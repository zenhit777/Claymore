# M11.1 — Addendum d'audit et corrections factuelles (2026-11-26)

Ce document complète le rapport `m11.1-clover-checkpoint-audit-2026-11-26.md`. En cas de divergence, le présent addendum prévaut pour les points explicitement corrigés ci-dessous. Il ne modifie ni les révisions upstream, ni les empreintes épinglées, ni le schéma des tenseurs.

## 1. Correction sur la taille des blocs SHA-256

Le rapport initial (§ 11, observation L2) indique que `sha256_file` traite les fichiers par blocs de 8 MiB via `MAX_CHUNK_BYTES`. Cette formulation est inexacte pour l'implémentation effectivement appelée par `CloverCheckpointInventory::verify_pinned_asset_hashes` :

- `verify_pinned_asset_hashes` appelle `sha256_file`.
- `sha256_file` appelle `sha256_reader`.
- `sha256_reader` utilise un tampon de lecture de **1 MiB** (`1024 * 1024` octets).
- `Sha256Stream::update` traite les octets reçus sans allocation proportionnelle à la taille totale du fichier.

Le constat de débit (environ 21 MB/s dans l'environnement décrit au rapport) reste une mesure observée, mais l'attribution à des blocs de 8 MiB est retirée. Aucune conclusion de sécurité ou de performance ne doit être tirée de cette taille erronée.

## 2. Défaut découvert et corrigé dans Sha256Stream

La revue du code a révélé un défaut dans `Sha256Stream::update` : lorsqu'un appel précédent laissait un bloc partiel en mémoire et que l'appel suivant apportait trop peu d'octets pour compléter les 64 octets, le chemin de traitement réinitialisait à tort le compteur de données tamponnées. Un lecteur conforme au trait Rust `Read` peut légalement renvoyer des lectures courtes ; l'implémentation devait donc préserver les fragments incomplets entre appels.

Correction appliquée sur `feat/m11-clover-foundation` :

- Commit : `7ee60fff9962c9b8cc05831eb854471deba05931`.
- Le bloc partiel est maintenant conservé si l'entrée suivante ne complète pas le bloc SHA-256.
- Le test de non-régression couvre plusieurs tailles de fragments (dont 1, 2, 7, 13, 31, 63 et 65 octets), des frontières de padding, ainsi qu'un lecteur qui renvoie volontairement des lectures courtes de 13 octets.
- CI Rust stable et Rust 1.86 : succès, run [45857457002](https://github.com/zenhit777/Claymore/actions/runs/45857457002), 2/2 jobs réussis.

**Limite de preuve à conserver :** la campagne de hachage complète de 69,3 GB consignée dans le rapport a été exécutée avant ce correctif. Les 28 empreintes ont également été calculées avec `sha256sum` et comparées à la table épinglée (28/28). Le nouveau test démontre le comportement corrigé sur les fragments courts ; le hachage intégral de 69,3 GB n'a pas été rejoué après le commit `7ee60fff`. Ne pas présenter le journal historique comme une exécution de ce nouveau SHA.
